# 📈 Growth direction -- Alexander

Personal context. **Not doctrine** -- it is about one engineer, so it could never live in `foundations/`, and it is not about this package, so it is not handbook either.

## The objective

Not "better at using coding agents." An **AI-native systems engineer and architect** who can design, build, evaluate and improve systems where engineers, deterministic software and agents cooperate on complex work reliably.

The trajectory:

prompting an agent -> configuring agents -> repeatable workflows -> controlled agentic systems -> reusable infrastructure that agents can themselves operate -> systems that build, evaluate and improve other systems

**With the guardrail:** avoid speculative architecture. *Learn -> apply in a focused project -> extract a reusable primitive only after it has proved useful.* Do not build a personal agent platform before real projects demonstrate the need for its abstractions.

**Project needs discover abstractions. Abstractions do not invent project needs.**

## What he is aiming at

Modeling problems as systems; discovering requirements and constraints; turning ambiguous workflows into explicit designs; provider-agnostic orchestration; explicit state and transitions; structured outputs and bounded agents; observable, reusable systems; **replacing opaque "AI magic" with deliberate orchestration.**

His own projects are the laboratories -- Life-OS, OMP/workbench tooling, Pi/runtime work, games, prototypes, and professional delivery work.

## The instinct he already has

He mentors engineers through tickets by asking rather than implementing. That is the same move coaching mode formalizes, which is why the coaching material transferred cleanly -- he is not learning the stance, only the recording discipline around it.

## Where he is most at risk

A natural systems and architecture orientation, which makes **stay in distribution** the guardrail that matters most for him specifically. Favour familiar structures that engineers and models both already understand. The rule is not "never abstract" -- it is that **an abstraction earns its complexity**, and the win is discovering the smallest useful primitive rather than building the elaborate framework because the architecture is attractive.

## How to work with him on this

- Do **not** supply more reading. Use deliberate practice on real engineering work.
- Use exercises that force an architectural decision he then has to defend.
- Prefer progressively harder real projects over theoretical ones.
- The end state is designing agentic systems **from first principles**, not reproducing any particular course's or framework's architecture.
